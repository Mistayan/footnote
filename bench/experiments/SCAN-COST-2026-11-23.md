# Change scan cost on large shares: decision rule (issue #549)

Written 23 November 2026, before any timed run, and committed on its own. Results go in
[SCAN-COST-RESULTS-2026-11-23.md](SCAN-COST-RESULTS-2026-11-23.md); changing a threshold below after seeing a result
requires a new dated rule and says so in the results.

## Question

`footnote index` re-reads and re-hashes (SHA-256) every file on each run to find what changed
(`crates/library/src/lib.rs`: `bounded_read`, `hash`, compare with the stored `sha256`). On a company file share of many
GB, is an unchanged re-scan dominated by reading and hashing, and which of these fixes it?

- **(a) today:** read and SHA-256 every file, compare with the stored hash.
- **(b) pre-check:** compare the file's size and modification time with the values recorded when it was last hashed;
  hash only files that look changed. The stored SHA-256 stays the source of truth: a file whose recorded stat matches
  is treated as unchanged, anything else is read and hashed as today. No stored hash changes, so (b) needs no new format.
- **(c) BLAKE3** in place of SHA-256 for enterprise corpora. Bench only: the free edition's stored hashes do not change.

## Safety design of (b), fixed before measuring

- The recorded stat is size, modification time in nanoseconds and one platform field (Unix: change time `ctime`, which
  `touch -r` cannot set back; Windows: creation time). Any difference means the file is read and hashed.
- **Racy stats:** a stat is trusted only when the file's modification time is at least 10 minutes older than the start
  of the scan that hashed it. Files written during or shortly before a scan (same-second rewrites, coarse timestamps such
  as FAT's 2 s, a file server whose clock is behind by up to Kerberos's default 5-minute tolerance) are hashed again on
  the next run, until they are old enough. A modification time in the future is never trusted.
- **Accepted gap:** a file rewritten with the same size and with its old modification time restored (some sync tools,
  `touch -r` on Windows) looks unchanged. Two fallbacks, both measured:
  - **rolling re-verify:** each run also hashes the files whose `(source id + run number) mod 16 = 0`, so every file
    is hashed at least once every 16 runs at about 1/16 of the full cost per run;
  - **full scan** on request (`Scan::Full` in the library API), which behaves like (a).
- The extractor check is unchanged: a file whose extractor version changed is re-extracted even when its stat matches.
- Missing stat data (an older database, a file indexed before this change) means a full hash for that file.

## Setup

- **Share:** generated by [`bench/scan-cost/make_share.py`](../scan-cost/make_share.py) (fixed seed), on the fastest
  local drive (C:, NVMe) outside the repository, deleted afterwards. Target 50,000 files and 20 GiB; if the drive has
  less than twice that free, scale down and record the scale. File mix: 40% `.pdf`, 15% `.png`, 15% `.jpg` (random
  bytes), 20% `.md`, 10% `.txt` (ASCII words, at most 1,000,000 bytes); log-normal sizes clipped to the product's 16 MiB
  limit; 1,000 folders; modification times spread over the past year.
- **Database:** seeded by `scan_cost seed` to the state a completed index leaves: one `sources` row per file with its
  SHA-256, status `indexed` and an extractor string the index accepts as current. No chunks are written (the unchanged
  path never reads them); this is stated as a limit.
- **Binaries:** release profile. (a) is `footnote_library::index` from `origin/main` at the commit this rule follows;
  (b) and `Scan::Full` are the new code at a frozen commit recorded in the results. Each arm has its own copy of the
  seeded database.
- **Dev versus held-out:** the code is written and tuned on a 2,000-file development share (seed 1). The commit is
  frozen before the held-out 50,000-file share (seed 549) is generated and measured.

## Measures

1. **End-to-end unchanged re-scan** of `index()` per arm: one discarded warm-up run, then 5 rounds with the arm order
   rotated each round; report the median, minimum and maximum. Arms: (a) today, (b) pre-check with rolling re-verify
   every 16 runs (steady state), (b) without rolling re-verify, and `Scan::Full`.
2. **Split of (a)** by an instrumented copy of today's loop (same calls: walk, `bounded_read`, `hash`, the same SQL):
   walk and metadata, read, hash, database. 5 runs, median. The sum must fall within 15% of (a)'s end-to-end median,
   or the gap is reported as unexplained.
3. **Cold read:** one pass reading every file with the OS cache bypassed (`FILE_FLAG_NO_BUFFERING`). The share fits in
   RAM (47.6 GiB), so warm runs are the best case for (a). Cold figures for (a) and (b) are estimates: the warm read
   time replaced by the uncached one, in proportion to the bytes each arm reads. A network share would be slower still.
4. **(c) hash cost:** standalone [`bench/scan-cost/hashbench`](../scan-cost/hashbench) reads each file into memory, then
   times SHA-256 (`sha2` 0.10, as shipped) and BLAKE3 (`blake3` 1.8, one thread, and multi-threaded per file), 3 runs,
   median. Its end-to-end effect is estimated as the arm's time minus its SHA-256 time plus the BLAKE3 time.
5. **Load:** CPU sampled for 10 s before each round and recorded. Above 30% average, wait 60 s and sample again, up to
   3 times, then run and flag the round.

## Decision rule

1. **(b) correctness gates**, as tests in `crates/library` that must all pass: content change with a new size; content
   change with the same size and a new modification time; a same-size rewrite inside the racy window with the
   modification time forced back to the recorded value; a future modification time; an extractor version change; a file
   deleted then restored; equivalence of the database after a mixed edit set between (b) and a full scan; `Scan::Full`
   and rolling re-verify each detecting a same-size rewrite with its old modification time restored.
2. **Ship (b) for every edition** if all gates pass and the held-out median of (b) with rolling re-verify is at most
   half of (a)'s median (at least 2x faster). Otherwise (b) does not ship and the result is recorded.
3. **Report how much of the gain survives each fallback:** rolling re-verify against (b) without it, and `Scan::Full`
   against (a).
4. **(c) BLAKE3 is recommended for the enterprise edition** only if it cuts the adopted mode's estimated unchanged
   re-scan by at least 25%. Its effect on a full re-hash (first index, full scan) is reported but does not decide. If
   recommended, the enterprise design records the algorithm with each hash (`blake3:` prefix), so editions and bundles
   never compare hashes of different kinds. If not, (c) is recorded as not needed.
5. Failures (a crashed run, a gate that fails, a scale cut) are results and are reported.
