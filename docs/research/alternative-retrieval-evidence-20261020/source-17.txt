I've got a query that only uses the HNSW index sometimes, and the query planner chooses not to use the index in two conditions per my observations:
Size of the LIMIT is too high
Values of the filters in the WHERE clause return a larger number of values
Here's some context of my setup:
I've got 3 tables -- tag, taggeditem and segment
I'm trying to filter on two columns on the tag tabled named category and name. I have btree indexes on both these columns
My HNSW index is built like so:
CREATE INDEX s_embedding_idx_shot ON segment USING hnsw (embedding halfvec_cosine_ops) WITH (m='32', ef_construction='128') WHERE ((category)::text = 'Shot'::text)
Here's how I'm doing my tag + vector search
BEGIN;
SET LOCAL hnsw.ef_search = 200;
SET LOCAL hnsw.iterative_scan = 'strict_order';
SET LOCAL hnsw.max_scan_tuples = 20000;
SET LOCAL hnsw.scan_mem_multiplier = 2;
-- EXPLAIN (ANALYZE, COSTS, VERBOSE, BUFFERS)
SELECT "segment"."id"
FROM "segment"
INNER JOIN "taggeditem"
ON ("segment"."id" = "taggeditem"."object_id")
INNER JOIN "tag"
ON ("taggeditem"."tag_id" = "tag"."id")
WHERE (
-- Tag filters
"tag"."category" = 'Cinematography'
AND "tag"."name" = 'Wide Framing'
-- Vector filter
AND "segment"."category" IN ('Shot')
AND ("segment"."embedding" <=> '[vector]') < 0.9)
ORDER BY ("segment"."embedding" <=> '[vector]')
LIMIT 100;
COMMIT;
With LIMIT 100, the vector index is not used.

Similar to above, I've also noticed a similar pattern with different numbers when I change the values that I'm filtering by. Specifically, I changed category='AssetType' and name='TV Ad' (stats on these below).

Hi @rsomani95, scanning more a vector index will be more expensive (which can happen with a higher limit or filters with a lower selectivity), and it looks like that's pushing it over the cost of other index scans. If you haven't already, try setting random_page_cost to 1.1. You can also use the pg_hint_plan extension to better control if an index is used.

The pg_hint_plan suggestion sent me down a bit of a rabbit hole. While it did force postgres to use the index, the quality of the results was quite inferior to brute force search (which was almost never the case when postgres decided to use the index by itself). I figured that part of the problem was that my filtering params were shaving off like 90% of the graph (not an exact number, but you get the point), so there really wasn't much space left to traverse within the HNSW graph. I ended up building a more tightly scoped index with some of the filtering params built in.
